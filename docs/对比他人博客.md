# AbingBlog Go 与 AI 后端学习路线

> 目标：以 AbingBlog 为长期练习项目，逐步接管 AI 生成的代码，建立独立开发、测试、部署和排障的 Go 微服务能力，并在此基础上学习 AI 应用后端工程。

## 项目定位

AbingBlog 不需要靠堆叠框架证明技术能力。它应当训练：

- Go HTTP 服务与分层设计
- 鉴权、事务、缓存和并发
- 测试、日志、部署与回滚
- 将不稳定的模型能力封装成稳定业务接口

可以使用 AI，但必须对进入仓库的代码拥有解释、修改、测试和排障能力。

## 如何接管 AI 代码

一段代码只有满足以下条件才算真正掌握：

- 能解释它解决的问题和完整调用链
- 能说明关键设计及替代方案
- 能列出主要失败场景
- 能脱离 AI 修改它
- 有可重复的测试方法
- 知道线上出错后先检查什么

接管顺序建议为：

`文章 → 分类标签 → 登录鉴权 → 访问统计 → 部署 → 缓存 → AI`

每次选择一条完整业务链，追踪 `router → handler → service → repository → MySQL`，然后自己补测试、增加规则、制造故障并完成排查。

## Java 开发者的 Go 学习重点

不必重复学习 MVC 和事务概念，重点掌握：

- interface 隐式实现，并在使用方定义小接口
- 显式错误处理、`errors.Is/As` 和错误包装
- `context.Context` 的超时、取消和跨层传递
- goroutine、channel、mutex 和数据竞争
- 表驱动测试、httptest、fake 和集成测试
- HTTP/数据库连接池与超时
- graceful shutdown、健康检查和结构化日志
- 幂等、重试、限流、链路追踪和回滚

避免 Java 式的过度抽象、无意义接口以及不受控的 goroutine。

## 项目迭代路线

### 第一阶段：可验证基线

独立启动数据库和服务，跑通登录与 CRUD，保证 `go test ./...`、`go vet ./...` 和构建稳定执行，并让 README 与代码现状保持一致。

### 第二阶段：接管核心业务

为 article、category、tag 编写测试，明确文章与标签的事务边界，完成前端真实数据联调，并使用 OpenAPI 统一 Go DTO 和 TypeScript 类型。

验收标准：关闭 AI 后，能在 60～90 分钟内独立增加一个小接口、测试并完成联调。

### 第三阶段：生产可靠性

引入正式数据库迁移、超时、优雅退出、request ID、结构化日志、登录限流、备份恢复和部署回滚演练。

### 第四阶段：Redis

先实现文章 Cache Aside 和访问量 `INCR + 定时批量落库`。只有真正需要跨服务解耦和可靠消费时才引入消息队列。

### 第五阶段：AI 写作建议

建议实现：

```http
POST /api/v1/admin/ai/article-suggestions
```

返回摘要、标签和 SEO 标题。AI 只提供建议，不自动覆盖正文或发布文章。

```go
type TextGenerator interface {
    Generate(ctx context.Context, req GenerateRequest) (GenerateResult, error)
}
```

业务层只依赖这个接口。DeepSeek、OpenAI 等模型是不同 adapter，供应商 SDK 不应扩散到 handler 和业务层。

必须包含鉴权、输入限制、超时、有限重试、结构化输出、调用记录和 Fake Provider 测试。

### 第六阶段：RAG 与工具调用

只索引已发布文章，按 Markdown 标题切块，回答必须携带引用。工具调用可用于创建草稿、推荐标签和检查链接，但发布、删除和权限变更必须由人确认。

## AI 使用规则

AI 可以生成重复 DTO、测试数据、CRUD 样板和进行代码审查。

事务边界、业务规则、context、并发、缓存一致性、安全判断和最终验收必须由自己负责。

接受 AI 代码前回答：

1. 为什么这样设计？
2. 失败时会发生什么？
3. 如何通过测试证明正确？
4. 我能否在没有 AI 的情况下修改它？

最终标准不是代码是否由 AI 生成，而是你能否读懂、解释、修改、测试、部署、排障，并为设计取舍负责。
